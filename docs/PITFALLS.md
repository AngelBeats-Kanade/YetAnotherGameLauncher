## 1. .NET 语义

- **CTS `Dispose` 后 `Cancel()`/`Token` 抛 `ObjectDisposedException`（2026-09-26 net10.0.11 三形态探针仲裁实锤：Dispose→Cancel、Dispose→Token、linked 源同款均抛；`Cancel()` 先于 `Dispose()` 才安全）**——此前的"no-op 不抛"记录系误证（2026-09-26 收拢批 review 发现两份一手证据冲突，scratch 探针复测裁决）。由此推论：①"收尾先 Cancel 再 Dispose"的顺序是**承重防御**而非风格偏好（`FfmpegVideoBackdropPlayer.PlayAsync` 收尾形态）；②摘除共享引用（Exchange 置 null）与 Cancel/Dispose 的竞态窗口内，持有方调用 `Cancel()` 必须有 `catch (ObjectDisposedException)` 防线（`StopCore` 先例），这不是"语义显式化"的装饰。
- **.NET 10 悬空符号链接三语义（2026-09-25 /tmp 探针实锤，Unix）+ 文件系统防护必须枚举目标全部既有形态**：①`File.Exists(悬空)=true`（跟随语义失灵——UmuPrefix 曾因此漏判悬空 pfx 链接致启动永久失败，F21；**同因反用也成立**：`!File.Exists(link)` 不是悬空探针，`WinePrefixBuiltinRepair` 用 `File.ResolveLinkTarget(link, true)` 结果 `is null || !Exists`，两种语义环境都正确）；②`File.GetAttributes(悬空)` 不抛、返回链接自身属性（`ReparsePoint=true`）；③`Directory.Delete(悬空)` 抛 `DirectoryNotFoundException`（**Unix** 删链接须用 `File.Delete`）。**Windows 删除语义相反**（2026-09-25 Windows CI 三用例实锤）：目录链接是 directory reparse point，`File.Delete`（DeleteFileW）对其报 `ERROR_ACCESS_DENIED`，删目录链接（含悬空）须用 `Directory.Delete`（RemoveDirectory 摘 reparse point 本身、不跟随目标——官方 reparse 删除语义；Windows 腿修复 bf577e6 已随 CI 双腿复跑确认，2026-09-26）。**Windows 经典语义不同：`File.Exists(悬空)=false`**——放在 `File.Exists` 门内的链接检查会被 Windows 悬空形态绕过（`PackageInstallerService.ExtractArchive` 的目标 reparse 检查因此必须无条件执行）。写解压沙箱/覆盖删除类防护时，目标位置的形态全集 = 不存在/真实文件/真实目录/工作链接/悬空链接/**硬链接**，逐一建模；`FileUtilities.IsReparsePoint` 的 catch 靠 IOException 臂即可覆盖 FNFE/DNFE（二者均为其子类，官方继承链探针复核）。硬链接无 ReparsePoint 标记、.NET 无可移植 link count API——防线用 P/Invoke 补齐（`FileUtilities.HardLinkCount`：Linux x64 走 stat(2) st_nlink、Windows 走 GetFileInformationByHandle nNumberOfLinks，探测失败按非硬链接放行；F43 已修 fe6ad8a）。**glibc 2.33 起才导出 stat 动态符号**（此前是 __xstat 内联包装，头文件内联、libc.so 无此符号）——DllImport 首调抛 EntryPointNotFound，与 DllNotFound（libc 不可加载）同入 fail-open 臂（ac9c525）。**递归目录枚举会跟入符号链接目录**（2026-09-27 真机实锤，F46）：`EnumerationOptions.RecurseSubdirectories=true` 对 symlink 目录照进不误——wine prefix 的 `dosdevices/z:` 指向 `/`，跟进即扫全盘并撞上 `/proc/<死进程>/cwd` 抛 `IOException: No such process` 崩掉整轮扫描；扫描可能含 `dosdevices` 的目录必须手动栈式递归且只进真实目录（`LinkTarget != null` 的条目只作候选、不入栈）。
- **Proton 兼容组件升级删除旧目录 = 所有由它创建的 prefix 的 builtin 链接全悬空，wine 任何 PE 进程启动即 `could not load kernel32.dll, status c0000135`（退出码 53）**（2026-09-27 实锤，F46）：签名特征是 wineserver/ntsync 正常起、服务 autostart 全 fixme、然后 PE 进程 53 退出——依赖安装的 `wine reg import` 与游戏本体启动同灭。三处坑：① `.update-timestamp` 已写 ≠ 链接已修——wine 自身的 builtin 实体化会半途而废（按字母序推进到 kernel32 之前中断）且版本标记已写不再重试，prefix 永久卡死，**重试无解**；② builtin 链接不止 system32/syswow64：windows 根、Fonts（`files/share/fonts` 与 `files/share/wine/fonts` 两类）、Program Files、command/ 等嵌套目录全都有（真机全 prefix 1337 条横跨各处，2026-09-27 实测），扫描必须全 prefix 递归；③ 修复 = 把悬空且目标含 `proton根/files/` 的链接重链到当前 Proton 树同相对路径（`WinePrefixBuiltinRepair`），换版时点（prune 删旧版前）就迁、存量靠依赖安装预检迁。`find -xtype l` 与 .NET `RecurseSubdirectories` 的跟进语义不同（前者不跟、后者跟），测量与实现可能看到不同的"悬空集合"。
- **改带选项结构体的 API 必须逐字段核对默认值与旧行为的差异，并用全形态对照测试钉住**（实锤 `FileUtilities.TryDeleteDirectory`）：为加 `IgnoreInaccessible` 换 `EnumerationOptions` 默认构造，其默认 `AttributesToSkip=Hidden|System` 在 Linux 上把点前缀条目（`.installed.ok`/`.yagl-*` 等，.NET 标记为 Hidden）从枚举剔除——含点文件的目录删不净、`Directory.Delete` 失败，UmuPrefix 清理路径全线回归。修复 = `AttributesToSkip = FileAttributes.None`。凡"为加一个选项换了构造形态"的改动，同结构体其余字段逐一过一遍。
- **IDE0005（未使用 using）有两类与肉眼相左的特例**：仅提供扩展方法的 using 构建期**不报**但可能必需；反之为必需 using 但肉眼看似未用（cref/扩展方法解析）。结论：删 using 以"删后编译"为准，IDE0005 的沉默不是充分证据。
- **`Process.StandardOutput.ReadToEnd()`（同步）会一直阻塞到子进程关闭 stdout，排在其后的 `WaitForExit(timeout)` 永远执行不到**——超时保护形同死代码，子进程挂起即卡死调用线程（实锤：`Program.cs` 启动期的 xrdb/hyprctl 查询曾会卡死 Main）。带超时的输出读取必须先 `ReadToEndAsync()` 再 `Wait(timeout)`，超时 Kill。
- **Windows 的 `CreateProcess` 对裸命令名自动补 `.exe`，而 `File.Exists`/`IsExecutableFile` 不会**：预检 PATH 上的裸命令（如 "hpatchz"）必须补试 `name + ".exe"`（`HpatchzApplier.ResolvePatchTool`），否则 Windows 误报工具缺失。Linux 还额外要求执行位（`FileUtilities.IsExecutableFile` 已含）。
- **写 catch 前查官方异常表全列；加 catch 后必须推演"接住之后呢"**：①`Process.Kill(entireProcessTree:true)` 官方抛 Win32Exception（无法终止/正在终止）+ AggregateException（子树未全终止），不止 InvalidOperationException；②同族 TOCTOU 异常类不同——`FileInfo.Length` 对文件缺失抛 FNFE、`File.OpenRead` 对父目录缺失抛 DNFE，catch 收窄即漏；③**接住异常不是终点**——接住后的下游路径（挂死/泄漏/分类丢失）要重新推演，等待类调用一律有界（实锤 F22-2 补 catch 后引入"Kill 真失败 → `WaitForExitAsync(None)` 永久挂"新风险）。
- **`System.Text.Json.JsonException` 直接继承 `Exception`，不是 `FormatException`**（2026-09-29 /tmp 探针实证，net10.0；F59 修复时按记忆假设"JsonException ⊂ FormatException"写 catch 过滤器，被红测当场击穿——测试红了两次才去实证）：catch 过滤器接畸形 JSON 响应必须显式列 `JsonException`；`FormatException` 在协议链路里对应的是畸形 URL 构造请求抛的 `UriFormatException`，是另一回事。凡要把"异常继承链"写进 catch/注释，先探针实证再落笔。
- **`DeflateStream`/`GZipStream` 默认 Dispose 会连带关闭内层流**（2026-10-18 实锤：流式 AES 解密器被
  `DeflateStream` 作用域提前 Dispose，随后的"读尽剩余密文再验 HMAC"直接 `ObjectDisposedException`）：
  内层流在解压器退出后还要继续用（补读尾部/校验/复用）时必须 `new DeflateStream(inner, mode, leaveOpen: true)`；
  该重载 .NET 9 起才有。另：增量 HMAC 用 `IncrementalHash.CreateHMAC(SHA1, key)`（`AppendData`/
  `GetHashAndReset`），`HMACSHA1` 本类没有增量方法。
- **UI 线程上同步等待 async（`.GetAwaiter().GetResult()` / `.Result` / `.Wait()`）会死锁：Avalonia 续体要回 Dispatcher，而阻塞的 UI 线程不泵队列**（2026-10-20 修复 `PersistWindowState`；同族事故 2026-09-06 设置页 `QueryWindowsAsync` 死锁 f38bbb6）。关闭/退出/托盘隐藏路径必须保证落盘时用**纯同步**原子写（`FileUtilities.WriteAtomic`），不要用"同步等待 async"；`ConfigureAwait(false)` 只是库侧缓解，不是根因修复——它管不到 App 层的阻塞调用，也挡不住未来某个库方法漏配。改这些路径前先按本条检查。
- **`await using` 不等于真异步；声明式 `await using var` 无法配置 `ConfigureAwait`**（2026-10-20 dotnet/runtime 源码复核）：`Stream.DisposeAsync` 默认同步调用 `Dispose()`；只读 `FileStream` / HTTP 响应流释放时没有真正的异步 I/O，写流（`FileStream` 写缓冲非空）才可能异步 flush。CA2007 对声明式 `await using` 的告警无法用 `ConfigureAwait(false)` 消除（编译器生成的 `DisposeAsync` 续体），只读流改 `using`；写流要保留异步释放时用块形式 `await using (stream.ConfigureAwait(false))`（本项目清零 pragma 的形态），或退回窄 pragma。
- **数组长度硬上限 `Array.MaxLength` = 2,147,483,591（2 GiB − 57 B）**（2026-10-17 net10.0.11 探针实证）：64 位机上 `new byte[Array.MaxLength]` 可分配，`+1` 抛 `OutOfMemoryException`（开 `System.GC.AllowVeryLargeObjects` 亦然）；**编译期常量**负长度是 CS0248 编译错，**运行期**算出的负长度进 `new byte[负]` 抛 `OverflowException`。规则：条目/缓冲尺寸上限常量取 ≤ `Array.MaxLength` 的值（先例 `MultiPartZipEntryReader.MaxEntryBytes = Array.MaxLength`——旧 512 MiB 上限曾在实机把 1199.9 MiB 的真实条目挡成更新中断；`WinZipAesReader` 的 inflate 上限同理 `Math.Min(uncompressedSize, (uint)Array.MaxLength)`）；外部读入的宽尺寸做 `(int)` 收窄前先判范围。
- **NativeAOT 不支持跨 OS 交叉编译**（2026-10-20 net10.0.113 实测）：Linux 上 `PublishAot=true -r win-x64` 直接报 `Cross-OS native compilation is not supported`。要在此环境产出 Windows 辅助程序（如诱饵桥 helper）只能用自包含单文件发布（`PublishSingleFile + SelfContained`，约 11 MB；Wine 下可运行）。
- **嵌套 `MSBuild` 任务会继承外层的全局 `RuntimeIdentifier`**（2026-10-20 复审实证）：Core 构建目标用 `<MSBuild Projects="tools/wine-parent-bridge/WineParentBridge.csproj" Targets="Publish">` 发布 win-x64 helper 时，`dotnet msbuild -p:RuntimeIdentifier=linux-x64` 的全局属性会压过 helper 工程自己的 `<RuntimeIdentifier>win-x64</RuntimeIdentifier>`，产出无 `.exe` 的 ELF（`EmbeddedResource` 指向缺失文件 → CS1566）。修法：在嵌套 `Restore`/`Publish` 的 `Properties` 里显式钉死 `RuntimeIdentifier=win-x64;SelfContained=true`，并在目标内重新 Restore（旧的异 RID `project.assets.json` 会让 publish 报 NETSDK1047）。实测 `dotnet publish -r linux-x64` 不触发该继承（helper 仍为 win-x64），但直接 `dotnet msbuild -p:RuntimeIdentifier=...` 会——两种入口都要覆盖（CI 的「Publish smoke」先跑外来 RID 的 msbuild 目标，再跑干净 publish 并断言嵌入资源）。

## 2. 文件系统与跨平台

- **Windows 占用/只读语义是跨平台更新的头号杀手**（Linux `rename()`/`unlink()` 总能成功，问题只在 Windows 暴露）：被占用或只读的文件会让 `File.Move(overwrite:true)` 抛 IOException/UnauthorizedAccessException、让 `Directory.Delete(recursive:true)` 整体抛异常。统一防线：原子写 `FileUtilities.WriteAtomicAsync`（解除只读+重试一次，任一环失败清理 .tmp 不残留——F68）、目录树 `FileUtilities.TryDeleteDirectory`（能删多少删多少）、下载落盘 `HttpFileDownloader.ReplaceDestination`（单独分类报"目标被占用"，绝不落进网络错误重试——重下多少遍都不会好；.temp 建流/写入/冲刷三处同款折算 F65）、背景落盘 `GameBackdropService` 换时间戳备用名。新增删除/覆盖代码先想这层。**同族新形态（2026-10-19 CI 双腿实锤）**：进程自己持有的普通读句柄也算占用——`FileStream` 未带 `FILE_SHARE_DELETE`（`FileShare.Read` 即不含）时，删除其所在目录树必须先释放该流（`using var` 作用域晚于删除动作即踩；Linux 的 unlink 语义让 Linux 腿对此恒绿，只有 Windows 腿会红——`DeltaPackageApplier` 载荷清理，2026-10-19 修：删除前显式 `Dispose`）。
- **`ZipFile.ExtractToDirectory` 在 Unix 把含 `\` 的 zip 条目名当字面文件名**（dotnet/runtime#98247，未修复）：Windows 打包器产出的包会在 Linux 解成安装根目录下的平铺垃圾文件，且"更新成功"。凡解包不可信外部 zip 必须手动遍历 `ZipArchive` 归一条目名（`PackageInstallerService.ExtractArchive`，顺带做 `..`/盘符穿越校验）。
- **切 PATH 必须用 `Path.PathSeparator`，不能硬编码 `':'`**：Windows 上盘符 `C:` 会被切开，`SearchPath`/`FindOnPath` 返回缺盘符的相对根路径（CI Windows 腿红过）。同理，`GameLauncherService.ValidateCommand` 仅在 `pathValue is null && Windows` 时跳过裸命令预检——测试注入 `pathValue:""` 必须仍走 PATH 扫描，否则预检/错误覆盖层用例在 Windows 上会假绿成「已启动」。
- **Windows 路径/注册表相关逻辑（自启动等）注意跨平台分支**（`OperatingSystem.IsWindows()`）：Linux 走 XDG autostart、Proton 兼容。
- **测试里的路径断言两侧必须统一分隔符再比较**：期望值 `Path.Combine(...)` 在 Windows 产反斜杠、实际值常被归一成正斜杠，Linux CI 恰好两侧同斜杠掩盖问题（Windows CI 一次红 11 个）。两类实锤：①只归一实际值没归一期望值（`UmuComponentProvisionerTests`）；②期望值拼相对路径硬编码 `/` 而生产经 `GetFullPath` 产原生分隔符，或反之配置模板里的 `{installDir}/saves` 展开是**字面替换**不归一（`LaunchParameterRoundTripTests`）。比较前两侧都过 `Replace('\\', '/')`。

## 3. 进程与日志

- **SystemProcessRunner 即启即走 + 输出日志三坑**：① `BeginOutputReadLine` 事件会丢 stderr——`WaitForExit()` 只排空 stdout，必须自管 ReadLine 泵到 EOF；② `using var process` 在方法返回即 Dispose，会掐断管道，日志模式须泵收尾后再释放句柄；③ 进程可能在 `EnableRaisingEvents=true` 布防前退出，此时 Exited 永不触发，布防后要补查 `HasExited`。（Windows 上测试轮询读生产进程正在写的日志须 `FileShare.ReadWrite` 打开——见 skills avalonia-headless-testing §5。）
- **wine reg import 的 V5 格式必须 UTF-16LE 带 BOM**（`FF FE`；无 BOM/ASCII 的 "Windows Registry Editor Version 5.00" 导入行为不保证）——Bottles 同款做法；`File.WriteAllText(path, content, Encoding.Unicode)` 自带 preamble。LF 换行可被接受，无需 CRLF。批量导入优先单 .reg 单次 `wine reg import`，逐键 `wine reg add` 每键一次 wine 调用（30+ 键 = 30+ 次 wineserver 会话）。
- **直调 Proton 内置 wine（`<proton>/files/bin/wine`，不经 `proton run`/umu 容器）时 freetype 库路径未配置**：GDI 字体枚举不可用（每次 wine 调用打 "cannot find the FreeType font library" 告警），但**注册表读写（reg import/query）与 wineboot 前缀初始化不受影响**（2026-09-27 dwproton-11.0-13 真机实测）。依赖安装只需读写注册表与文件系统，故直调可行；需要字体渲染/GDI 的场景必须走 umu/Proton 完整容器环境。
- **`WINEDLLOVERRIDES=mscoree,mshtml=`（等号结尾 = 禁用）防 wine 首次触碰 prefix 时弹 mono/gecko 安装框**：无人值守进程里弹框即挂起。依赖安装器对每次 wine 调用都带上，属纵深防御（prefix 已由游戏首启初始化时通常不会触发）。
- **wine 拒绝在非本用户所有的目录创建 prefix**（"'/tmp' is not owned by you, refusing to create a configuration directory there"，owner 安全检查；sticky 目录即触发）——测试/脚本把 WINEPREFIX 指向 `/tmp` 会静默失败（exit 0 但 prefix 没建），必须放家目录或校验 `drive_c` 是否真的出现。
- **umu/steamrt 容器内的 locale：宿主 LANG 原样穿透，且宿主 locale 数据在容器内可用**（2026-09-29 实测）——pressure-vessel 的 "Using glibc from provider system … Arbitrarily using provider locales" 警告只关乎混合架构 glibc 的选择面，**不代表宿主 locale 不可用**：容器内 `/usr/bin/locale -a` 实列 zh_CN.utf8 且全类别解析为 zh_CN。排查游戏内编码问题先经 `_v2-entry-point -- <命令>` 在容器内跑 `locale`/`printenv` 实测，不要望警告文生义。
- **Wine 的运行时 ANSI/OEM 代码页由 glibc 生效 locale 推导，prefix 注册表里的 `Nls\CodePage`（ACP/OEMCP）与 `Nls\Language`/`Nls\Locale` 都是写出值而非读入值**（2026-09-29 实测；证据层级：「不读回」方向 = 源码溯源（部分）——ntdll init_locale 经 `setlocale(LC_CTYPE/LC_MESSAGES)` → locale.nls 表映射为 init 路径溯源，未逐行穷尽全文件；注册表只是同步落盘的 artifact 属行为反推。把 `Nls\Language`/`Nls\Locale` 0409 改 0804 对游戏行为无影响，对照实验 F58）。观测容器内 Wine 实际代码页的技巧：`wine cmd /c chcp` 的**消息语言与输出编码**是 locale/CP_ACP 的直接观测面（管道重向下打印的页码数字不可信；该机制括注为推断——经 CP 0=CP_ACP 转换，未核 wine cmd 转换调用链，观测结论本身不受影响）。
- **Wine 对 `UpdateProcThreadAttribute` 的 `lpValue` 保存指针而非拷贝值**（2026-10-20 真机对照实验，F89）：`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` 的父进程句柄变量必须保持分配直到 `CreateProcessW` 返回——helper 先 `Marshal.AllocHGlobal(IntPtr.Size)` 写句柄、调用后立即 `FreeHGlobal`，后续创建以 `ERROR_INVALID_HANDLE (6)` 失败（同一 helper 保活即成功、提前释放即失败，两组真机实录）。Windows 语义为拷贝、提前释放无害；跨平台代码一律保活到调用返回（多占 8 字节）。
- **console 子系统 PE 在无终端的 Wine 链上会开 conhost 黑窗**（2026-10-20 真机复现，F89）：`--subsystem,console` 的桥 helper 经 `_v2-entry-point → proton waitforexitandrun` 启动时出现全屏 `conhost.exe`（`hyprctl clients` 实录 `class='conhost.exe'`、标题含 `yagl-parent-bridge.exe`），且 helper 自身 stderr 被吞、黑窗是纯副作用。后台 helper 一律 GUI 子系统（.NET `OutputType=WinExe` 或 `-Wl,--subsystem,windows`）；诊断走退出码与重定向日志。
- **后台编排器透传子进程退出码时，不能用它的退出码判断编排器本身是否失败**（2026-10-20 复审）：诱饵桥 helper 在游戏进程创建后把游戏退出码原样返回（启动校验拒绝是 5），launcher 把任意非零都当桥故障会误报"桥坏了"；反过来 `WaitForExit:false` 的恒 0 又会把桥启动失败报成「已启动」。用 helper 写出的启动状态文件（`READY` 表示游戏进程已创建；`ERROR:<code>:<message>` 表示创建前失败）区分阶段，只有 READY 之前才算桥失败。状态文件写失败或 helper 在写状态前崩溃时，launcher 只能等满超时（默认 30 s）后报错——这是不用退出码判定换来的延迟，不能退回"看退出码/立即返回 0"。
